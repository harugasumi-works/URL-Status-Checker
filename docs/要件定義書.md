# URL Status Checker 要件定義書

## 1. システム概要

URL Status Checker は、ユーザーが入力したURLを複数件まとめてチェックし、HTTPレスポンスの状態を一覧表示するデスクトップアプリケーションである。

本システムは、イミュータブルなデータ型を中心に処理を組み立てる **Data-Oriented Programming（DOP）** と、JavaFXの状態管理、セッション管理、入出力、サービス連携などをクラスとして管理する **Object-Oriented Programming（OOP）** を組み合わせた **DOP + OOP** の構成を採用する。

チェック処理はJava 26の`StructuredTaskScope`と仮想スレッドを利用して並行実行し、JavaFX Application Threadをネットワーク処理でブロックしない。

## 2. 対象範囲

### 2.1 対象

- URLの手入力
- `.txt`ファイルからのURL一括取込
- 複数URLの並行ステータスチェック
- Scan中のキャンセル要求
- URL、Status、Code、Detailによる結果一覧表示
- 同一URLの重複登録防止
- URLの個別削除および全件削除
- 成功／失敗件数の集計
- JSON / CSV形式でのエクスポート
- 20秒間隔のセッション自動保存
- アプリケーション終了時のセッション保存／破棄／キャンセル
- 前回セッションの復元
- セッションファイル破損時のバックアップ

### 2.2 対象外・制約

- URL本文の取得・解析
- HTTPメソッドの選択（GET以外のメソッド）
- リダイレクト経路そのものの詳細分析
- 認証情報付きURLの認証方式の管理
- URLごとの個別編集機能
- `.txt`以外のファイル形式からの一括取込

## 3. 機能要件

| ID | 要件 |
|---|---|
| FR-01 | ユーザーはURL入力欄からURLを1件ずつ追加できる。 |
| FR-02 | EnterキーでURLを一覧へ追加できる。 |
| FR-03 | URL入力は前後空白、BOM、スキーム表記などを正規化して検証する。 |
| FR-04 | `http://`および`https://`のURLを受け付ける。スキーム未指定の場合は`https://`として扱う。 |
| FR-05 | 不正URLおよび重複URLは一覧へ追加せず、理由をユーザーへ通知する。 |
| FR-06 | `.txt`ファイルからURLを読み込み、一括取込ダイアログへ表示できる。 |
| FR-07 | 一括取込では、追加された件数、重複件数、不正件数を表示し、拒否された行を修正可能な状態で残す。 |
| FR-08 | Scan実行時、一覧中のPendingおよびScannedの全URLを再チェックする。 |
| FR-09 | 複数URLを並行してチェックする。 |
| FR-10 | 1回のスキャンで最大50件までネットワーク要求を同時実行する。 |
| FR-11 | Scan中は通常の操作バーを無効化し、別領域のCancel scanボタンを有効化する。 |
| FR-12 | ユーザーが削除した行について、遅れて到着したスキャン結果を一覧へ復元しない。 |
| FR-13 | 結果をURL、Status、Code、Detailとして一覧表示する。 |
| FR-14 | HTTP応答または通信結果をSuccessまたはFailとして分類する。 |
| FR-15 | 全スキャン結果からtotal、successCount、failureCountを集計する。 |
| FR-16 | スキャン結果をJSONまたはCSVとしてユーザー指定のファイルへエクスポートできる。 |
| FR-17 | エクスポート時、URLおよびリダイレクト先に含まれる認証情報を出力しない。 |
| FR-18 | CSV出力では、表計算ソフトによる数式実行につながるセル値を無害化する。 |
| FR-19 | データ変更後、20秒間隔でセッションを自動保存する。 |
| FR-20 | 自動保存はJavaFX Application Thread以外で実行し、保存中の追加変更を失わないようにする。 |
| FR-21 | アプリケーション起動時、保存済みセッションを復元するかユーザーに確認する。 |
| FR-22 | セッションJSONが破損している場合、破損ファイルをバックアップへ移動し、アプリケーションの起動を継続する。 |
| FR-23 | アプリケーション終了時、セッションを保存する、破棄する、終了をキャンセルするのいずれかを選択できる。 |

## 4. URL入力・正規化要件

入力されたURLは`ContentParser.normalize()`によって正規化する。

- 前後の空白を除去する。
- BOM（`U+FEFF`）を除去する。
- `http://`および`https://`を認識する。
- スキーム未指定の場合は`https://`を補う。
- ホスト部分は小文字化する。
- 末尾の単独`/`は除去する。
- 国際化ドメイン名は`IDN.toASCII()`によって検証可能な形式へ変換する。
- IPv6リテラル、ポート番号、アンダースコアを含むホスト名などを現行のバリデーション規則に従って扱う。

URL検証に失敗した入力はScan対象にならない。

## 5. スキャン結果要件

### 5.1 Success

- HTTPステータスコードが300未満の場合は`Success`とする。
- タイムスタンプ、HTTPステータスコード、レイテンシ（ms）を保持する。

### 5.2 Fail

- HTTPステータスコードが300以上の場合は`Fail`とする。
- URL生成失敗、接続失敗、接続タイムアウト、応答タイムアウト、割り込みなども`Fail`として保持する。
- HTTP応答を取得できない場合の`statusCode`は0とする。
- HTTPエラーコードについては、400、401、403、404、405、408、410、429、500、502、503、504などを具体的な理由へ変換し、それ以外はクライアント／サーバーエラーとして分類する。
- リダイレクト先に認証情報が含まれる場合、表示・出力される理由文字列から認証情報を除去する。

`HttpClient`は`Redirect.NORMAL`を利用するため、通常のHTTPリダイレクトは自動追跡される。

## 6. 非機能要件

### 6.1 応答性

- ネットワーク処理はJavaFX Application Thread以外で実行する。
- スキャン結果は各タスク完了時に逐次UIへ反映する。
- 最大同時実行数は50件とする。

### 6.2 タイムアウト

現行実装のタイムアウト値は以下のとおりとする。

| 項目 | 値 |
|---|---:|
| HTTPリクエストタイムアウト | 4秒 |
| TCP/TLS接続タイムアウト | 2秒 |

### 6.3 可用性・データ保持

- 1件のURLの失敗が、他URLのチェック中止を直接引き起こさないこと。
- 予期しない`RuntimeException`も可能な限り`Fail`へ変換し、行と結果を失わないこと。
- セッション保存には一時ファイルと原子的な移動を使用する。
- 直近のセッションバックアップを最大5件保持する。

## 7. セキュリティ要件

- セッション保存、JSON出力、CSV出力、リダイレクト先表示ではURL中のユーザー情報・パスワードを除去する。
- CSVでは`=`, `+`, `-`, `@`などで始まる値（先頭空白を含む）を無害化し、表計算ソフト上の数式として解釈されることを防止する。

## 8. テスト要件

- DOPで扱うドメイン変換、集計、シリアライズ、URL検証などの純粋な処理について単体テストを実施する。
- `SessionRow`、`ScanService`、`ScanJoiner`、URL認証情報除去などの境界処理について単体テストを実施する。
- 実ネットワークを使用する統合テストは、通常の単体テストとは分離して実行できるものとする。
- テストでは、実際の時刻値が不要なケースについて`(Instant) null`を渡してテストデータを簡略化する場合がある。この値は本番データを意味するものではなく、テスト対象の集計・変換ロジックを簡潔に検証するための選択である。

## 9. 前提・実行環境

- JDK 26
- JavaFX 26
- Gradle 9.7.1
- Java preview featuresを有効化してビルド・テスト・実行する。
- アプリケーションの実体は`StatusCheck/lib/src/main/java/statuscheck/ui/main/Main.java`にある。
