## 2. ドメインモデル

### 2.1 `ScanRequest`

```text
record ScanRequest(
    String id,
    String requestedURL
)
```

スキャン対象を識別するIDと正規化済みURLを保持する。

### 2.2 `Outcome`

```text
sealed interface Outcome permits Success, Fail
```

具体的な状態は以下のrecordで表現する。

```text
Success(Instant timeStamp, int statusCode, long latency)
Fail(Instant timeStamp, int statusCode, String reason)
```

本番スキャンでは失敗時の`statusCode = 0`を「HTTP応答を取得できなかった」ことの表現として利用する。

### 2.3 `ScanResult`

```text
record ScanResult(
    String id,
    ScanRequest context,
    Outcome outcome
)
```

`context`を保持することで、非同期に到着した結果を元の行へ対応付けられる。

### 2.4 `RowItem`

```text
sealed interface RowItem permits Pending, Scanned
```

- `Pending(ScanRequest)` — 未チェックまたは再チェック待ち
- `Scanned(ScanResult)` — 最新のチェック結果を保持

### 2.5 `Report`

```text
Report(
    CountStat stats,
    List<ScanResult> successes,
    List<ScanResult> failures
)
```

`Report.summarize()`はリスト件数から`CountStat`を生成する。

## 3. URL正規化・検証

### 3.1 `ContentParser.normalize()`

処理順序の概略は以下である。

```text
raw
 ↓
nullなら空文字
 ↓
BOM除去 + trim
 ↓
http:// / https:// を分離
 ↓
authority / path / query / fragment を分離
 ↓
authorityを小文字化
 ↓
単独の末尾 / を除去
 ↓
スキーム未指定なら https:// を補う
 ↓
normalized URL
```

### 3.2 `ContentParser.isValidURL()`

以下を検証する。

- 空文字でないこと
- 空白文字を含まないこと
- `http`または`https`スキームであること
- authorityが存在すること
- ポート番号が数字であること
- IPv6リテラルまたは有効なホスト形式であること
- 国際化ドメイン名を`IDN.toASCII()`へ変換できること
- ASCII化したホスト長が253文字以内であること

## 4. SessionStore詳細

### 4.1 保持状態

```text
knownUrls   : URL重複判定用Set
indexById   : id → items上のインデックス
items       : ObservableList<RowItem>
itemsView   : 外部公開用unmodifiable ObservableList
scannedCount: Scanned行数
hasData     : Scanned結果が1件以上存在するか
```

### 4.2 `addPending()`

1. JavaFX Application Threadであることを確認する。
2. `knownUrls`でURL重複を確認する。
3. ID重複時は`IllegalArgumentException`とする。
4. `indexById`へ追加する。
5. `RowItem.Pending`を`items`へ追加する。
6. `onChanged`を実行してautosaveをdirtyにする。

### 4.3 `completeScan()`

スキャン結果が別スレッドから届くため、`FxThread.run()`を利用してJavaFX Application Threadへ処理を移す。

```text
result.context().id()
        ↓
indexById lookup
        ↓
存在しなければ無視
        ↓
PendingならscannedCount++
        ↓
items[index] = RowItem.Scanned(result)
        ↓
onChanged()
```

削除済みIDは`indexById`に存在しないため、遅延したScanResultによって復元されない。

### 4.4 `remove()`

対象IDを`indexById`から除去し、`items`から行を削除する。行削除によって後続行のインデックスがずれるため、`reindexFrom()`で再構築する。

### 4.5 `clear()`

全行、IDインデックス、URL重複集合、Scanned件数を初期化する。既存行があった場合のみ変更通知を行う。

## 5. ScanService詳細

`ScanService`はJavaFX側のScanライフサイクルを管理する。

### 5.1 `requestsFrom()`

`RowItem.Pending`はその`ScanRequest`を使用し、`RowItem.Scanned`は`ScanResult.context()`から元の`ScanRequest`を取り出す。したがって、ScanはPendingだけでなくScannedも再チェックする。

### 5.2 `start()`

```text
FxThread.require()
 ↓
既にcurrent taskがあれば何もしない
 ↓
SessionStoreから全ScanRequest取得
 ↓
空なら通知して終了
 ↓
今回対象IDをSet化
 ↓
Task<Void>生成
 ↓
background threadでScanOperator.scanAll()
 ↓
current設定 + scanning=true
 ↓
Thread開始
```

成功時は`ScanSummary.format()`によって対象IDだけを集計し、キャンセル時は`Scan cancelled.`、予期しないTask失敗時は例外概要を通知する。

### 5.3 `cancel()`

現在実行中の`Task`に対して`cancel(true)`を呼び出し、割り込みを伴うキャンセルを要求する。

## 6. ScanOperator詳細

### 6.1 同時実行制限

```text
MAX_CONCURRENT_REQUESTS = 50
```

共有`Semaphore`でネットワーク要求数を制限する。

### 6.2 1 URLの処理

```text
ScanRequest
 ↓
LinkBuilder.requestFactory()
 ↓
HttpRequest.build()
 ↓
Semaphore.acquire()
 ↓
HttpClient.send()
 ↓
InputStream close
 ↓
statusCode判定
 ↓
Success / Fail
```

### 6.3 URL生成失敗

`LinkBuilder.requestFactory()`または`URI.create()`などで例外が発生した場合は以下の形でFailへ変換する。

```java
new Fail(Instant.now(), 0, ErrorSpecs.describe(e))
```

### 6.4 HTTP結果判定

```text
status < 300       → Success
300 <= status < 400 → Fail("Redirect not followed" ...)
400 <= status < 500 → Fail(reasonFor(code))
status >= 500      → Fail(reasonFor(code))
```

通常の3xx応答は`HttpClient.Redirect.NORMAL`によって追跡されるため、最終的に3xxが返った場合はリダイレクトを完了できなかったケースとしてFailへ分類される。

### 6.5 通信例外

| 例外 | Fail理由 |
|---|---|
| `InterruptedException` | `The scan was interrupted.`。その後割り込み状態を復元 |
| `HttpConnectTimeoutException` | TCP/TLS接続タイムアウトの説明 |
| `HttpTimeoutException` | サーバー応答遅延の説明 |
| `IOException` | 接続切断の説明 |
| その他の`RuntimeException` | `Unexpected error: ...` |

### 6.6 `Fail((Instant) null, 0, ...)`について

テストコードでは、時刻や実際のHTTPコードがテスト対象ではない場合に、例えば次のようなfixtureを使用することがある。

```java
new Fail((Instant) null, 0, "...")
```

これは本番処理でその値を生成するためではない。本番の`ScanOperator`は実際には`Instant.now()`を使用し、HTTP応答がない場合などに`statusCode = 0`を付与する。

テスト fixtureでは、時刻生成や意味のないHTTPコードを毎回用意する複雑さを避けるために、この簡略化を選択している。

## 7. ScanJoiner詳細

`ScanJoiner`は`StructuredTaskScope.Joiner<ScanResult, Void>`を実装する。

### `onComplete()`

- Task状態が`SUCCESS`でなければ`onTaskFailure.run()`を実行する。
- 正常終了なら`subtask.get()`で`ScanResult`を取得する。
- `onResult.accept(result)`で結果を即時通知する。
- `false`を返して、他タスクをキャンセルしない。

`result()`は`Void`を返す。最終結果の蓄積は`ScanJoiner`自身ではなく、`SessionStore`および後段の`SessionOutput` / `ReturnOutput`で行う。

## 8. Scan結果・出力詳細

### 8.1 現在の出力取得

`SessionOutput.current()`は`SessionStore.items()`から`RowItem.Scanned`だけを抽出して`ScanResult`のリストを作る。

### 8.2 `ReturnOutput.fromResults()`

```text
results.empty
   → null

otherwise
   ↓
Successを抽出
   ↓
Success以外をFailとして抽出
   ↓
ExecutionResult生成
   ↓
ReturnOutput.output()
```

### 8.3 JSON

`JsonDto.convert()`はJacksonでJSON Treeへ変換した後、URLフィールド（`requestedURL` / `url`）を再帰的に検査し、`UrlCredentialSanitizer.removeCredentials()`で認証情報を除去する。

### 8.4 CSV

列順は以下で固定する。

```text
timeStamp,url,outcome,statusCode,latencyMs,reason
```

Successを先に、Failを後に出力する。

`safeSpreadsheetCell()`は、先頭空白を除去して確認した文字が`=`, `+`, `-`, `@`のいずれかなら、先頭に`'`を付与する。

## 9. ExportService / ExportFile詳細

`ExportService`は`ScanOutput`を取得して形式別のエクスポータを選択する。

```text
source.get()
 ↓
null → NOTHING_TO_EXPORT
 ↓
JSON / CSVを選択
 ↓
LazyConstant.get()
 ↓
ExportFile
 ↓
FileChooser.showSaveDialog()
 ↓
ユーザー指定ファイルへ書き込み
```

ユーザーがダイアログをキャンセルした場合は`CANCELED`とする。`IOException`その他の例外は`FAILED`へ変換して通知可能な形式へ整える。

## 10. ImportService / ImportURLs詳細

### 10.1 `ImportURLs`

OSのFileChooserで`.txt`ファイルを選択し、内容を読み込んで一括取込画面のテキストエリアへ設定する。BOMを除去し、空白区切りで読み込んだURLを改行区切りへ整形する。

### 10.2 `ImportCheck`

各行を以下へ分類する。

```text
blank   → 無視
http/https/other input
        ↓
ContentParser.normalize()
        ↓
isValidURL()
        ├─ true  → valid
        └─ false → rejectedLines + invalid
```

一括取込画面では、追加成功分をStoreへ渡した後、拒否された行だけをテキストエリアに残す。

## 11. セッション詳細

### 11.1 `Session`

`Session`は`SessionStore`と`AutoSaveService`を構成し、Store変更時にautosaveをdirtyにする。

### 11.2 `AutoSaveService`

内部状態は概略以下のとおり。

```text
version         : 変更バージョン
savedVersion    : 保存済みバージョン
reportedVersion : UIへ報告済みバージョン
inFlight        : 保存中件数
```

変更がある場合、UIスレッドでスナップショットを取得し、単一threadのExecutorへ保存処理を委譲する。

保存成功後、スナップショット作成時点より新しい変更があれば再保存する。保存失敗時に自動再試行を無条件でループさせず、次回タイマーまたは明示的な保存機会に委ねる。

### 11.3 `AutoSave`

保存先は以下である。

```text
${user.home}/StatusCheck/session.json
```

保存時は`session.json.tmp`へ書き込んだ後、可能であれば`ATOMIC_MOVE`で本体へ移動する。

読込失敗時は破損ファイルを`session-YYYYMMDD-HHmmss[-N].json.bak`形式へ退避し、最大5件のバックアップを維持する。

### 11.4 `SessionRow`

`RowItem`からJSON保存用のプリミティブなrecordへ変換し、読込時に再び`RowItem`へ戻す。

保存前にはURL認証情報を除去するため、セッションファイルへ平文のユーザー名・パスワードを残さない。

## 12. スレッドモデル

```text
JavaFX Application Thread
  ├─ UI操作
  ├─ SessionStore操作
  ├─ snapshot取得
  └─ UI更新

url-scan thread
  └─ ScanOperator.scanAll()
       └─ StructuredTaskScope
            └─ per-request task
                 └─ HttpClient.send()

session-autosave
  └─ ファイル保存
```

非FXスレッドから`SessionStore.completeScan()`が呼ばれても、`FxThread.run()`によってUI更新はJavaFX Application Threadへ移される。

## 13. エラー処理詳細

| 発生箇所 | 処理 |
|---|---|
| URL正規化／検証 | `false`を返し、UIで入力エラーとして通知 |
| `HttpRequest`生成 | `Fail`へ変換 |
| 接続タイムアウト | `Fail`へ変換 |
| リクエストタイムアウト | `Fail`へ変換 |
| 通信I/Oエラー | `Fail`へ変換 |
| スキャンタスク異常終了 | `onTaskFailure`でカウントし、対象行はPendingのまま残る |
| エクスポートI/Oエラー | `ExportService.Result.FAILED`へ変換 |
| セッション保存失敗 | `Autosave failed`を表示し、保存処理自体の例外をログ／通知 |
| セッション読込失敗 | 破損ファイルをバックアップへ退避し、空セッションで起動継続 |

## 15. 設計上のトレードオフ

### 15.1 DOP + OOPの混在

`Outcome`や`ScanResult`をrecord／sealed typeにしてデータを明確に保つ一方、`SessionStore`や`AutoSaveService`など状態を持つ責務まで無理に関数化しない。これにより、DOPの可搬性とOOPのライフサイクル管理を両立する代わりに、「純粋DOP」という一貫したモデルは採用していない。

### 15.2 ScanJoinerが集計を持たない

以前のようにJoiner自身でSuccess/Failを蓄積するのではなく、完了通知だけを担当させている。これによりUIへ早く結果を反映でき、並行処理層からUI実装を切り離せる。一方、最終的な集計やエクスポートには別の変換処理が必要となる。

### 15.3 `SessionStore`のインデックス管理

`id → index`のMapによりScanResultをO(1)で対象行へ戻せる。代わりに行削除時には後続要素のインデックスを更新する必要がある。

### 15.4 最大50並行

仮想スレッドを利用しているが、無制限にHTTP要求を発行すると相手先やローカル資源へ過剰な負荷をかけ得る。そのため`Semaphore(50)`で上限を設ける。これは大量URLを処理する際の総所要時間と資源使用量のバランスを取るための制約である。

### 15.5 LazyConstant

JSON/CSV変換は保存時に初めて必要になるため遅延生成する。繰り返しSaveを選択した場合は変換済みデータを再利用できるが、生成済み文字列をメモリへ保持する。

### 15.6 テストfixtureの簡略化

`Fail((Instant) null, 0, ...)`は、時刻やHTTPコードの正しさではなく、分類・集計・シリアライズなど別の性質を検証したいテストで使用できる。fixtureを簡潔にすることで、テストの意図をコード上で明確にする代わりに、fixtureだけを見ると本番状態との違いを読み取る必要がある。

## 16. 既知の制限事項

- URL個別編集機能はない。誤ったURLは削除して再登録する必要がある。
- 一括取込は`.txt`に限定される。
- URL本文の内容までは検査せず、HTTP応答の成否を中心に判定する。
- 通常のリダイレクトは追跡するが、リダイレクトチェーンそのものを結果として記録する機能はない。
- `HttpClient.Redirect.NORMAL`の動作に依存するため、すべての異常なリダイレクト構成を個別に説明するものではない。
- 同時実行数は50に固定されている。
- JSON/CSVはメモリ上に生成してから保存するため、極端に大きなスキャン結果ではメモリ使用量が増える。
- セッションはローカルユーザー領域の`session.json`へ保存される。ユーザーによるファイルシステム障害やディスク容量不足を完全には吸収しない。
- URLの認証情報は出力から除去するが、入力されたURLそのものを外部通信へ使用する仕様であり、認証情報を含むURLを入力しないことを前提とするのが望ましい。
- 現行`build.gradle.kts`の`application.mainClass`には旧パッケージ名`statuscheck.ui.firstlayer.Main`が残っており、現在のソース`statuscheck.ui.main.Main`と一致していない。

## 17. 開発・テスト上の注意

本プロジェクトはソロ開発であり、単体テストおよび実装確認によって把握できた表面上の不具合を中心に修正している。テスターによる継続的な探索的テスト、異なるOS・環境・負荷条件での網羅的な検証、予期しない利用手順によるバグの発見までは十分に行っていない。

したがって、現状の修正範囲は主として**表面化したバグの修正**であり、テスター不在によって発見できていない潜在的な不具合が残っている可能性がある。
