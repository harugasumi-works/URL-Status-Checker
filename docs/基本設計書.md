# URL Status Checker 基本設計書

## 1. 設計方針

本システムは、DOPだけで全体を構成するのではなく、**DOP + OOP** を採用する。

DOPの考え方は主に`domain`層のデータ表現と純粋な変換処理へ適用する。一方、JavaFXのUI状態、セッション保持、バックグラウンド保存、サービス間の依存関係など、ライフサイクルや外部資源を扱う部分はOOPとしてクラスへカプセル化する。

したがって、`ScanRequest`、`ScanResult`、`Outcome`、`Report`などは「データを表現する」ことを中心とし、`SessionStore`、`AutoSaveService`、`ScanService`、`ExportService`などは状態や外部処理を管理する。

## 2. システム構成

| 領域 | 主な役割 | 代表クラス |
|---|---|---|
| `ui` | JavaFX画面、ユーザー操作、UI状態 | `Main`, `WindowInit`, `MainUI`, `MainButtons`, `AppState` |
| `service` | スキャン・取込・エクスポートのユースケース調整 | `ScanService`, `ScanSummary`, `ImportService`, `ExportService` |
| `session` | 一覧状態と自動保存状態の管理 | `Session`, `SessionStore`, `AutoSaveService`, `SessionOutput` |
| `concurrency` | 並行スキャンの実行と完了通知 | `ScanOperator`, `ScanJoiner` |
| `domain` | イミュータブルな要求・結果・状態データ | `ScanRequest`, `ScanResult`, `Outcome`, `RowItem`, `Report`, `SessionRow` |
| `net` | HTTPリクエスト／クライアント生成 | `LinkBuilder` |
| `io` | ファイルI/O、JSON/CSV変換、セッションI/O | `ExportFile`, `ReturnOutput`, `JsonDto`, `CsvDto`, `AutoSave`, `ImportURLs` |
| `util` | URL検証、入力解析、エラー記述、FXスレッド制御 | `ContentParser`, `ImportCheck`, `ErrorSpecs`, `FxThread`, `UrlCredentialSanitizer` |

## 4. メイン処理フロー

```text
入力
  ↓
ContentParser / ImportCheck
  ↓
ScanRequest
  ↓
SessionStore.addPending()
  ↓
ScanService.start()
  ↓
ScanService.requestsFrom()
  ↓
ScanOperator.scanAll()
  ↓
StructuredTaskScope + ScanJoiner
  ↓
ScanResult
  ↓
SessionStore.completeScan()
  ↓
JavaFX Application Threadへ反映
  ↓
SessionOutput.current()
  ↓
ReturnOutput.fromResults()
  ↓
Report + Lazy JSON/CSV
  ↓
ExportService → ExportFile
```

## 5. UI設計

### 5.1 メインウィンドウ

メイン画面は以下の3領域で構成する。

1. 上部のツールバー
2. 中央の結果テーブル
3. 下部の通知・キャンセル・自動保存ステータス領域

ツールバーには以下を配置する。

- Scan
- Save
- URL入力欄
- Clear all
- Bulk Import

下部には以下を配置する。

- Cancel scan
- 入力／処理通知
- 自動保存状態

### 5.2 結果テーブル

テーブルは`RowItem`を表示対象とし、以下の4列を持つ。

| 列 | 内容 |
|---|---|
| URL | 正規化されたURL |
| Status | `Pending` / `Success` / `Fail` |
| Code | HTTPステータスコード。未スキャン時は`—` |
| Detail | Successではレイテンシ、Failでは失敗理由 |

並び替えはJavaFXの`SortedList`を介して行い、`SessionStore`内部のデータ順序そのものは変更しない。

### 5.3 削除

- Deleteキーで選択行を個別削除する。
- Clear allで全行を削除する。
- 削除後、該当URLを再登録できる。
- スキャン中に削除された行へ遅れて結果が届いた場合、その結果は無視する。

## 6. URL取込設計

### 6.1 手入力

`MainUI`が入力を受け、`ContentParser.normalize()`と`ContentParser.isValidURL()`を使用して検証した後、`SessionStore.addPending()`へ渡す。

### 6.2 一括取込

`Bulk Import`ではモーダルウィンドウを表示する。

- テキストエリアへURLを複数行入力する。
- `.txt`ファイルを選択して内容を読み込める。
- `ImportService`が各行を検証する。
- 有効URLは`SessionStore`へ追加する。
- 無効行は`rejectedLines`としてテキストエリアに残す。
- 重複件数と不正件数をユーザーへ通知する。

## 7. スキャン設計

`ScanService`はUIからのScan操作と並行実行層の間を仲介する。

1. JavaFX Application Thread上で`start()`を呼び出す。
2. `SessionStore.items()`から全行の`ScanRequest`を取得する。
3. 空の場合は通知して終了する。
4. `Task<Void>`を作成してバックグラウンドスレッドで`ScanOperator.scanAll()`を実行する。
5. 結果到着時は`SessionStore.completeScan()`でUI状態を更新する。
6. 完了後、`ScanSummary`が今回対象の件数を集計して通知する。

## 8. 並行実行設計

`ScanOperator.scanAll()`は各`ScanRequest`を`Callable<ScanResult>`へ変換し、`StructuredTaskScope`へforkする。

`ScanJoiner`は各タスクの完了を受け取り、正常終了した`ScanResult`を`onResult`へ渡す。タスク自体が異常終了した場合は`onTaskFailure`を実行する。

各ネットワーク処理は共有`HttpClient`を利用し、`Semaphore`によって同時実行数を50件に制限する。

## 9. HTTP通信設計

`LinkBuilder`は以下を設定する。

- GET
- HTTP/1.1ではなく`HTTP_3`を優先
- 通常のリダイレクトを追跡する`HttpClient.Redirect.NORMAL`
- リクエストタイムアウト4秒
- 接続タイムアウト2秒
- User-Agent
- Accept
- Accept-Language

HTTPレスポンスはボディを完全に利用するのではなく、`InputStream`として受け取り、不要になった時点で閉じる。

## 10. 結果・集計設計

### 10.1 ドメインモデル

```text
ScanRequest
  ├─ id
  └─ requestedURL

ScanResult
  ├─ id
  ├─ context: ScanRequest
  └─ outcome: Outcome

Outcome
  ├─ Success(timeStamp, statusCode, latency)
  └─ Fail(timeStamp, statusCode, reason)
```

`Outcome`はsealed interface、`Success`と`Fail`はrecordとして定義する。

### 10.2 集計

`Report.summarize()`が`ExecutionResult`から以下を算出する。

```text
total        = successes.size() + failures.size()
successCount = successes.size()
failureCount = failures.size()
```

## 11. エクスポート設計

`SessionOutput.current()`が現在の`Scanned`行だけを`ScanResult`へ変換し、`ReturnOutput.fromResults()`がSuccessとFailを分離して`ExecutionResult`を生成する。

`ReturnOutput.output()`は`Report`と、遅延評価されるJSON/CSVデータを持つ`ScanOutput`を生成する。

`LazyConstant`によってJSON/CSV変換は必要になった時点で一度だけ実行する。

CSVはSuccessを先に出力し、その後Failを出力する。

## 12. セッション・自動保存設計

`Session`が`SessionStore`と`AutoSaveService`を組み合わせる。

`SessionStore`は以下を管理する。

- `ObservableList<RowItem>`
- URL重複判定用`knownUrls`
- IDから行位置への`indexById`
- Scanned件数
- データ有無プロパティ

データ変更時に`Session`が`AutoSaveService.markDirty()`を呼び出す。

`AutoSaveService`は20秒周期のタイマーから呼び出され、UIスレッドでスナップショットを取得してから単一のバックグラウンドExecutorで保存する。保存中にさらに変更があった場合は、その変更を次回保存対象として維持する。

終了時の`saveNow()`のみ、終了処理との整合性を保つため呼び出し元スレッドが完了を待機する。

## 13. セキュリティ設計

`UrlCredentialSanitizer`を共通利用し、次の出力経路からURLのユーザー情報を除去する。

- セッションファイル
- JSON
- CSV
- リダイレクト先を含むFail理由

`CsvDto`では、表計算ソフトで数式として評価される可能性がある値をアポストロフィ付きへ変換する。

## 14. テスト設計

主なテスト対象は以下とする。

- URL正規化・検証
- URL認証情報除去
- ImportService
- ScanService
- ScanJoiner / ScanOperator
- Report
- JSON / CSV出力
- SessionRowのシリアライズ／復元
- LazyConstant
- 実ネットワークを使用した統合テスト

実時刻を検証する必要のないテストでは、`Success((Instant) null, 0, 0)`や`Fail((Instant) null, 0, ...)`のような値を使用することがある。これは本番で`null`時刻や`0`ステータスを生成することを意味せず、時刻そのものがテスト対象ではないケースのデータ生成を簡略化するための選択である。

## 15. 設計上のトレードオフ

### 15.1 DOP + OOP

すべてを純粋関数として扱うと、JavaFX、ObservableList、ファイルI/O、Executorなどのライフサイクル管理がかえって複雑になる。このため、外部状態を扱う部分はOOPへ寄せ、値の変換・分類・集計はDOP寄りに保つ。

### 15.2 `ScanJoiner`のコールバック方式

Joiner自身にSuccess/Failのコレクションを持たせず、完了した`ScanResult`をコールバックで即時通知する。これによりUI更新までの遅延を抑えられる一方、最終集計は別の層で行う必要がある。

### 15.3 `SessionStore`による状態管理

IDとインデックスをMapで保持することで、スキャン結果を対象行へ戻す処理を高速化する。一方、行削除時には後続行のインデックスを再構築する必要がある。

### 15.4 JSON/CSVのLazy生成

エクスポートデータを毎回生成せず、最初に要求された時だけ変換することで不要な処理を省く。一方、巨大な結果をエクスポートする場合は、変換済み文字列をメモリ上に保持する。

### 15.5 テスト用`null`値

`Fail((Instant) null, 0, ...)`などは、テスト対象が時刻や実HTTPステータスではない場合にデータ作成を簡略化するために使用する。テスト fixtureの可読性と準備コストを優先した設計上の選択である。
