Đánh giá Repository
Concurrent Programming Project Using Java 26

Đánh giá theo trạng thái repository hoàn thiện • Junior Project

Bản đánh giá này chỉ tập trung vào trạng thái repository sau khi đã hoàn thiện các phase chính và sau khi biết rõ đây là một junior project. Không sử dụng bản đánh giá ban đầu về trạng thái chưa hoàn thiện của repository.

1. Kết luận tổng quát

Đây là một junior project có tham vọng kỹ thuật cao hơn mức thông thường. Project không chỉ là một demo multithreading: nó là một desktop application nhỏ, có domain model, HTTP execution, structured concurrency, aggregation, export, JavaFX UI và test suite.

Điểm mạnh cốt lõi là project chọn một bài toán đủ nhỏ để kiểm soát nhưng đủ phức tạp để buộc người viết giải quyết concurrency, immutable data, failure handling, UI threading, I/O và testing.

Implementation chưa đạt production-grade và còn một số điểm architectural chưa sạch. Tuy nhiên, đối với junior project, những hạn chế này là hợp lý. Đáng chú ý hơn là repository thể hiện quá trình tiến hóa: implementation → phát hiện vấn đề → refactor → decoupling → testing.

2. Project đang giải quyết bài toán gì?

Application nhận danh sách URL, thực hiện HTTP request đồng thời, phân loại kết quả, tổng hợp report và cho phép export dữ liệu.

  • Input → ScanRequest
  • ScanRequest → HTTP execution
  • Nhiều HTTP tasks → StructuredTaskScope
  • Tasks → CustomJoin
  • Kết quả → Success / Fail
  • ExecutionResult → Report
  • Report → JSON / CSV
  • JavaFX UI điều khiển workflow và hiển thị kết quả

3. Domain model

Domain model là một trong những phần tốt nhất của repository. Project sử dụng records cho các value/data objects và sealed interface để mô hình hóa Outcome.

Cấu trúc khái niệm:

Outcome
├── Success
└── Fail

Cách này có lý do về domain: Success và Fail là một tập hợp trạng thái đóng, đồng thời mỗi variant có thể mang dữ liệu riêng. Đây là một use case hợp lý cho sealed types + records, thay vì dùng feature chỉ để khoe Java 26.

Đánh giá: 8.5/10.

4. Concurrency architecture

Đây là phần mạnh nhất của project. Operator tạo các tasks và đưa chúng vào StructuredTaskScope; CustomJoin thu thập kết quả khi các subtasks hoàn thành.

Mô hình:

Operator
↓
StructuredTaskScope
├── Task 1 → HTTP
├── Task 2 → HTTP
├── Task 3 → HTTP
└── …
↓
CustomJoin
↓
ExecutionResult

Điểm quan trọng là project phân biệt task failure với application-level failure. Một HTTP 404 không nhất thiết làm Java task thất bại; nó có thể được biểu diễn như một ScanResult chứa Fail. Ngược lại, exception thực sự làm subtask không thành công đi qua failure handling của Joiner.

Đánh giá: 9/10.

5. Network layer và HTTP semantics

Project sử dụng java.net.http.HttpClient, timeout và status-code classification. Kết quả HTTP được chuyển về Outcome thay vì đẩy exception handling xuống toàn bộ application.

Mô hình hiện tại đơn giản và phù hợp với mục tiêu học concurrency: status dưới 400 được xem là Success, 4xx/5xx là Fail; malformed URL và network failure cũng được đưa về failure model.

Nếu đánh giá như một monitoring tool chuyên nghiệp, vẫn thiếu nhiều semantics như retry policy, rate limiting, 429/Retry-After, latency distribution, DNS/TLS categorization chi tiết và benchmark quy mô lớn.

Đánh giá: 7.5/10 cho production use; phù hợp với junior learning project.

6. Data-Oriented Programming

Triết lý “data stays as data” tương đối nhất quán. ScanRequest → ScanResult → ExecutionResult → Report được xử lý như một pipeline data transformation, thay vì đẩy behavior vào mọi domain object.

Đây là lựa chọn phù hợp với bài toán hiện tại. Tuy nhiên, DOP không mặc nhiên tốt hơn OOP; giá trị của nó ở đây nằm ở việc nó phù hợp với pipeline xử lý kết quả.

Đánh giá: 8/10.

7. JavaFX và concurrency integration

Project không block JavaFX Application Thread bằng cách chạy scan trong javafx.concurrent.Task. Callbacks được đưa về JavaFX thread bằng Platform.runLater().

Boundary hợp lý:

JavaFX Application Thread
↓
Background Task
↓
StructuredTaskScope
↓
HTTP tasks
↓
CustomJoin
↓
Platform.runLater()
↓
JavaFX UI

Điểm này đặc biệt đáng giá trong một project concurrency vì nó chứng minh concurrency phải coexist với event-driven UI, không chỉ chạy trong console.

Đánh giá: 8.5/10.

8. Decoupling và dependency boundary

Phase 8 là một tín hiệu tốt về tư duy kiến trúc. CustomJoin không hard-code dependency vào JavaFX; thay vào đó nhận callback thông qua Consumer<ScanResult> và Runnable.

Điều này giữ concurrency layer độc lập với UI layer. Với một junior project, đây là một quyết định thiết kế đáng ghi nhận vì nó cho thấy repository đã được refactor sau khi nhận ra coupling.

9. Testing

Repository có các test cho CSV export, CustomJoin, integration, JSON export, LazyConstant và Report. Đáng chú ý là có cả unit tests và real-network integration test.

Điều này cho thấy project đã đi qua vòng development tương đối đầy đủ: thiết kế → implementation → failure/bug → refactor → test.

Đánh giá: 8/10.

10. Những điểm chưa hoàn hảo

Static mutable state trong Operator: Operator vẫn giữ một số state static mutable như task list/request list. Với một scan duy nhất thì có thể hoạt động, nhưng thiết kế này làm giảm isolation và gây khó khăn nếu muốn chạy nhiều scan độc lập hoặc đồng thời.

Operator có nhiều responsibility: HTTP client, request construction, task creation, structured scope, aggregation và một phần export preparation tập trung vào một class. Với project nhỏ điều này chấp nhận được, nhưng về lâu dài có thể tách thành các component rõ hơn.

Failure callback còn thô: Runnable chỉ báo rằng task failure xảy ra, nhưng không mang request ID, URL hay exception. Một failure event trong hệ thống lớn hơn thường cần context.

HTTP semantics còn đơn giản: Chưa phải một monitoring system đầy đủ: retry, rate limiting, backoff, latency metrics và phân loại lỗi mạng chi tiết chưa phải trọng tâm.

Chưa có performance evidence: Project thể hiện concurrency architecture nhưng chưa chứng minh throughput/latency/memory ở quy mô 1,000–10,000 URL.

Một số Java 26 features có giá trị học tập cao hơn giá trị nghiệp vụ: LazyConstant là ví dụ: nó phù hợp để nghiên cứu Java 26 nhưng memoization cho export có thể không tạo nhiều giá trị nếu mỗi report chỉ export một lần.

11. Đánh giá việc sử dụng Java 26

Việc dùng Java 26 nhìn chung có lý do rõ ràng:

  • records → immutable data
  • sealed interfaces → closed Outcome hierarchy
  • pattern matching → xử lý các data variants
  • StructuredTaskScope → structured concurrent execution
  • virtual threads → I/O-bound HTTP tasks
  • LazyConstant → nghiên cứu lazy/memoized computation

Do đó đây không đơn thuần là project nhồi Java 26 features. Những feature quan trọng nhất, đặc biệt StructuredTaskScope, gắn trực tiếp với bài toán.

12. Scope discipline

Project giữ scope tương đối tốt. Nó không cố biến URL checker thành một hệ thống enterprise gồm Spring Boot, database, Redis, Kafka, Docker, authentication và microservices.

Đối với một junior project, đây là ưu điểm. Bài toán nhỏ nhưng đủ khó cho phép người viết tập trung vào Java và concurrency thay vì infrastructure.

Đánh giá: 9/10.

14. Nếu đánh giá đúng theo chuẩn Junior

Không nên dùng production-grade architecture làm thước đo chính. Static mutable state, responsibility hơi rộng, failure model đơn giản và thiếu benchmark vẫn là các hạn chế kỹ thuật thật, nhưng chúng không làm project trở thành một project kém.

Điểm đáng giá hơn là người viết đã bắt đầu đặt câu hỏi về architecture. Việc refactor CustomJoin để loại bỏ coupling với JavaFX là ví dụ rõ. Một junior chưa viết được mọi boundary hoàn hảo là bình thường; một junior biết nhận ra boundary chưa tốt và sửa nó là tín hiệu tích cực.

Nhận định phù hợp nhất là: đây là một junior project có tham vọng kỹ thuật cao hơn mức junior thông thường, nhưng implementation vẫn mang dấu vết của junior. Hai điều này hoàn toàn có thể cùng đúng.

Câu hỏi phỏng vấn

“Tại sao bạn dùng StructuredTaskScope thay vì ExecutorService?”

Vì mỗi HTTP check là một child task thuộc cùng một scan operation; lifecycle của child tasks nên được gắn với scope của parent operation.

“Tại sao Outcome là sealed interface?”

Vì success/failure là một closed set trong domain này và mỗi variant mang dữ liệu khác nhau.

“Tại sao CustomJoin dùng ConcurrentLinkedQueue?”

Các subtasks complete concurrently và onComplete() có thể được gọi từ các thread khác nhau, nên accumulator phải an toàn khi concurrent mutation → tốt.

“Tại sao Platform.runLater() nằm ở callback chứ không nằm trong CustomJoin?”

Vì concurrency layer không nên biết JavaFX tồn tại; UI layer cung cấp callback phù hợp.

“Điểm yếu lớn nhất của architecture hiện tại là gì?”

Operator đang giữ static mutable state và làm quá nhiều responsibility.
